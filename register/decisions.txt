@ratified Lang = Rust
@ratified-why Rejected C because undefined behaviour (uninitialised reads, signed overflow) can make the same source behave differently at different optimisation levels — a direct threat to determinism. Rejected Go for GC jitter in a fixed tick and randomised map iteration. Rejected Python for runtime-only error detection and A55 CPU ceiling.
@ratified Xen = The board computes state; the browser computes pixels
@ratified-why The RK3566 CPU and 1 GB RAM never touch rendering. Client-side canvas costs the board a few KB of JSON instead of per-frame CPU and memory.
@ratified Det = Determinism is a mandatory engine property
@ratified-why Chosen so replay-as-test is possible. Enforced by integer-only sim math, ordered containers, in-repo PRNG, and a cross-architecture hash comparison in CI.
@ratified Pkg = One static aarch64 binary
@ratified-why Measured 2026-11-11: a browser-playable networked game is 304 KB on disk and 1.9 MB RSS, zero crates. The deployable is a single file with no glibc dependency.
@ratified Http = Hand-rolled HTTP over std, no framework
@ratified-why Measured at +19 KB disk and +216 KB RSS over the bare Rust floor. A framework would cost more than the game.
@endratified

@decision A1
@group blocking
@title What "clean" means
@context This is your slot and it gates the most. It decides how the game is installed
and supervised on the board, what account it runs as, what survives a reboot, and
what "reset to a clean machine" means. It also decides whether deployment is a copy
or a package manager's job.
@option system | Installed into /usr/local with a root systemd unit. Conventional, survives reboot, but writes outside home and needs root to change anything.
@option user | Single binary in ~/bin run by a systemd --user unit with linger enabled. No root after install, survives reboot, everything in one place, easy to delete.
@option container | Podman/Docker image. Isolation and reproducibility, at the cost of a container runtime on a 1 GB board — a daemon, ~30-60 MB idle, and a dependency the whole design was avoiding.
@option bare | No supervisor. Started by hand or by a shell script. Smallest surface, but nothing restarts it and nothing tells you it died.
@agent Recommend the user-scoped unit: no root after install, one binary, one unit file, and rollback is restoring the previous file. A container contradicts the single-binary finding unless you want isolation for its own sake.
@ruling user
@rationale light enough to keep it to start in boot , yet easy enough to remove or 'install' , ideally either no dependency or easy to handle dependency
@end

@decision A2
@group blocking
@title Tick model — does the world move on its own clock?
@context Decides whether the simulation advances when nobody is looking. This shapes
the engine loop, the save model, and what the player experiences when they return
after a day away.
@option realtime | The world ticks continuously at a fixed rate whether or not anyone is connected. Rimworld-like. Requires the server to actually run a loop, and a bounded cost per hour of wall time.
@option step | The world advances one tick per player action or command. Rogue-like. Cheapest and simplest to make deterministic, but nothing happens between commands, so a colony cannot live while you are away.
@option hybrid | Continuous while someone is connected, paused otherwise, with an option to fast-forward on return. More code, but it is what most players of this genre actually expect.
@option catchup | Advance on demand: when a player returns, simulate the elapsed interval in a burst before serving the first frame. Deterministic and cheap at rest, but a long absence creates a spike of work that must be bounded.
@agent Recommend hybrid, with catchup capped. Fixed ticks counted in integers keep determinism intact; the real cost is a loop that must survive the SD card's write latency and never let wall-clock values into state.
@ruling realtime
@rationale try realtime first with speed 1 to 3 , i want to see how well it can perform
@end

@decision A3
@group blocking
@title What the player is
@context This is the single biggest determinant of what gets built. Dwarf Fortress,
Cave of Qud and Rimworld share a genre but give the player entirely different
relationships to the world. It decides the interface, the failure model and the
systems worth building first.
@option colony | The player manages a group: assign work, build, survive. Systems are jobs, needs, stockpiles, threats. Rimworld/DF-fortress-like.
@option character | The player is one being in a larger world: move, act, die, re-roll. Systems are the world's, not yours. Cave of Qud-like.
@option observer | The player watches a world generate and live, nudging rather than commanding. Systems are history, factions, emergent drama. DF-legends-like.
@option mixed | A character inside a colony — one body to command among many agents. Most expensive, most distinctive.
@agent No recommendation: this is preference, not engineering. Everything downstream is cheaper once it is ruled.
@ruling character
@rationale character within the world .
@end

@decision A4
@group blocking
@title World representation
@context Decides how space is stored and therefore what pathfinding, line of sight and
map generation cost. On 1 GB with an A55, a dense grid that is too large is the
fastest way to blow a budget.
@option dense | One array cell per tile, fixed rectangular world. Trivial indexing, trivially serialisable, memory is size x size exactly. Cost scales with area whether or not anything is there.
@option chunk | Dense tiles grouped into chunks, only active chunks resident. Standard game design; more code, much better scaling to large worlds, and it complicates determinism slightly because chunk load order must be fixed.
@option graph | Places and links rather than a tile field. Very small and fast for a text game, but forbids spatial simulation like fields of view or projectile paths.
@option hybrid | A dense local area the player inhabits, plus a coarse graph for the wider world. Two representations to keep in sync, which is a permanent source of bugs.
@agent Recommend chunk if the world is meant to be big, dense if it is meant to be deep-but-small. The measurement to make first is memory per tile: at 8 bytes a tile, a 512x512 world is 2 MB, which is affordable; 4096x4096 is 134 MB, which is not.
@ruling chunk
@rationale an string of seed at the start of each 'run' , then generate the world on start , which take care the 'roough' shape , and stuff like terrain and faction , then when player actually enter into an 'tile' , it got generated .
@end

@option ascii | A character grid on a canvas with colour and a fixed font. Reads as retro, allows a real map, and costs almost nothing because the client draws it.
@option tiles | 2D sprite tiles. Legible and approachable, but introduces an asset pipeline, a size budget, and the question of who makes the art.
@option mixed | Text panel plus a small ASCII or tile minimap. The usual answer for this genre, and the most code.

@decision B1
@group shaping
@title Save format
@context The manifesto currently holds determinism as an engine property while the
save format stays open. A pure seed-plus-input save is tiny but is only valid for the
exact engine build that produced it, so an upgrade would destroy a long-lived world.
@option snapshot | Periodic full world snapshot. Survives upgrades, self-describing, but size grows with the world and the write bursts are large.
@option replay | Seed plus complete input log. Kilobyte saves, replay doubles as a test, but any simulation change invalidates every existing save.
@option snapdelta | Snapshot plus the input log since it. Upgrade-tolerant like a snapshot, small like a delta. More moving parts and two formats to version.
@option both | Snapshot format for the player, replay log kept separately for debugging. Redundant deliberately: the log cannot be loaded as a save but can reproduce one.
@agent Recommend snapdelta for the player plus a retained replay log for diagnostics. This is the note already recorded in the manifesto.
@ruling replay
@rationale how about an string plus small file , or maybe just one file contain the string or sha hashes , then use compute power to recompute the world state back out . [round 2: seed plus recompute , confirmed replay ; D4 versioned already accepts that upgrading destroys old worlds]
@end

@decision B2
@group shaping
@title Persistence cadence and crash policy
@context The SD card is the likeliest component to wear out or corrupt, and it fails
quietly. This decides write volume, what a power cut costs, and whether the card is a
consumable you rotate.
@option periodic | Autosave every N ticks to a temp file and rename. Bounded write rate, loses at most N ticks on a crash, and rename-over is atomic.
@option on-change | Write every state change as a journal entry. Near-zero loss, but write volume tracks gameplay and can be very high.
@option on-exit | Save only when the player leaves or the service stops. Almost no wear, and a power cut loses the session.
@option manual | The player chooses when to save. Honest to the genre, hostile to a modern player.
@agent Recommend periodic with an atomic rename and a measured interval. The number to ratify is bytes written per simulated day, measured on the real A1 card, not guessed.
@ruling periodic
@rationale auto save in-game , plus the ability to do manual save for the player . [round 2: resolved to periodic , meaning autosave on an interval plus a manual save button]
@end

@decision B3
@group shaping
@title Target scale — the budget driver
@context Every budget in the manifesto is a function of this. Picking a scale that is
too large is the failure mode the whole "manufactured constraint" principle exists to
prevent, and it is easy to pick one that sounds modest and is not.
@option small | A single settlement: tens of agents, thousands of items, a bounded map, one continuous run of hours.
@option medium | Hundreds of agents, tens of thousands of items, a region, runs lasting days.
@option large | Thousands of agents, a persistent world with history generation, runs lasting months.
@agent Recommend writing this as four concrete numbers — map cells, live agents, live items, uninterrupted run length — because a target expressed in adjectives cannot be measured against. The POC budget suggests all three tiers are affordable in RAM; CPU per tick is the real limit.
@ruling small
@rationale demo phase , a town is enough . the intent is to build the tooling first , prove everything work , then try to scale up much , much later
@end

@decision B4
@group shaping
@title Content data format
@context Manifesto P5 says content is data and the core is an interpreter. This
decides what you will actually be editing when you add a creature, an item or a rule,
and whether content lives inside the binary or beside it.
@option line | A custom line-oriented format, parsed by hand. Zero dependencies, human-editable, and completely under your control. No tooling, no schema checker.
@option toml | TOML stands for Tom's Obvious Minimal Language — a config format readable by humans, widely understood and easy to diff in review. Needs a parser, so either a crate or hand-written.
@option json | Widely supported and easy to emit, but verbose and hostile to hand editing, and no comments.
@option embedded | Content compiled into the binary with include_str!, so the deployable stays one file and content cannot drift out of sync.
@agent Recommend the custom line format, embedded at build time. It keeps the crate count at zero, it is the only option where the parser is small enough to trust, and it is the same choice already made for this register.
@ruling toml
@rationale toml for now , probably external tools with nice gui much later , not the point for now
@end

@decision B5
@group shaping
@title How hard to hold determinism
@context Determinism is ratified as a property, but how it is proven and for how long
is not. This decides CI cost and what happens when a test fails years later.
@option arch | Assert hash equality in-process only. Cheap, catches most regressions, and would not catch an architecture-specific divergence.
@option xarch | Assert equality across x86 and aarch64 under qemu on every build. Catches the failure mode that motivated the choice, at the cost of a qemu step in CI.
@option fixtures | Keep recorded replay fixtures and re-assert them for every historical version. Strongest, and the fixture set grows without limit.
@option all | All of the above, with fixtures pruned to a rolling window.
@agent Recommend xarch plus a small rolling fixture set. Cross-architecture equality is the test that earns its keep; unlimited fixtures become a maintenance burden nobody reads.
@ruling xarch
@rationale this is not final , as this need to be test out live during version rolling
@end

@decision B6
@group shaping
@title Real-time channel
@context Pong used polling because it has no handshake, no framing protocol and no
crypto, and it was measured at 666 req/s on one thread with zero memory growth. That
was a proof of concept, not a ruling for a game with a moving world.
@option poll | The client asks for state at an interval. Simplest, no framing, works everywhere, and short-lived connections never wedge. Latency floor equals the interval and cost scales with clients times frequency.
@option sse | Server-Sent Events: one long-lived text stream from server to client, with player input posted separately. No handshake crypto, native in every browser, one connection per client, and the server must handle many open sockets at once.
@option ws | WebSocket. Bidirectional over one socket, the industry answer, and it costs a SHA-1 handshake plus a framing protocol — the first real dependency or the first hand-written crypto in the project.
@agent No strong recommendation yet: measure sse against poll first. Polling already works; the question is whether a moving world makes the interval visible, and that is a player-experience question, not a throughput one.
@ruling ws
@rationale again not final , need actual testing
@end

@decision B7
@group shaping
@title Client rendering technology
@context All of these draw on the player's machine, so none costs the board anything.
It decides what the client code looks like and what you can do with it later.
@option canvas2d | A 2D canvas. Direct control of pixels, trivial to scale with CSS, and the Pong client already proves it.
@option dom | HTML elements for everything. Free accessibility and text selection, poor fit for a tile map with many cells.
@option webgl | WebGL. Enormous headroom, and a large amount of scaffolding for a text game that does not need it.
@agent Recommend canvas2d, which is already proven in this project, with DOM overlays for text panels and controls.
@ruling canvas2d
@rationale should be good
@end

@decision X1
@group content
@title How entities are built — the uniform model
@context Every creature, item and the player should share one mechanism, so any entity can act on and be acted on by any other.
